Try the real API

The dashboard above only reads seeded demo data. The API itself is a full multi-tenant CRUD service — register your own account and it behaves like any other job-tracker backend would. 

# 1. register
curl -X POST $API/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email": "you@example.com", "password": "a-strong-password"}'

# 2. log in (OAuth2 password flow, form-encoded)
curl -X POST $API/auth/login \
  -d "username=you@example.com&password=a-strong-password"

# 3. use the token
curl $API/applications \
  -H "Authorization: Bearer <token>"

Or skip curl entirely and use the interactive Swagger UI — it has an "Authorize" button wired up to the same JWT flow.

Design notes

The parts of this that were actual decisions, not defaults.

  • Multi-tenancy Every company, application, and interview stage is scoped to owner_id; ownership is checked on every read and write, not just enforced at creation.
  • Public demo layer The /demo/* routes are read-only and serve one fixed seeded account, kept separate from the authenticated CRUD API so the live dashboard has zero write access to real data.
  • Rate limiting Login, registration, and the public demo endpoints are throttled per-IP with slowapi to blunt credential-stuffing and scraping.
  • Migrations, not create_all Schema changes ship as Alembic revisions; the container runs alembic upgrade head on boot instead of trusting SQLAlchemy to reconcile the schema.
  • Tests hit the real stack pytest spins up a throwaway SQLite file per test and drives the API through FastAPI's TestClient — no mocked ORM layer.
